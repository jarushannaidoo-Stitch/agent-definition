Behavior-first test strategy:
- Derive tests from the frozen acceptance criteria and actual user journeys. For each criterion, identify the entry point, action, observable outcome and plausible wrong behavior the test must reject. Reuse existing proof where it already covers the criterion. Do not add tests to increase counts or coverage percentages, mirror implementation details, assert fixture values, or duplicate coverage without a distinct failure risk.
- Favor end-to-end tests as the primary evidence that a feature works. Exercise the real application through its supported UI, API or CLI and follow the journey through the owned components and services to the final result. For browser features, use the real browser and normal application build. A rendered component with mocked application behavior is component coverage, not end-to-end proof. Reuse the established harness; raise missing infrastructure, interfaces or file scope to CoS rather than changing the frozen contract.
- Assert the user's outcome, not merely that a click occurred, a mock was called, a URL matched or a page mounted. Verify the expected data and identity/scope, resulting navigation or state, persisted change, or usable generated artifact as applicable to the criterion. Cover the approved failure and recovery paths and relevant existing behavior. Keep each journey focused on a clear outcome.
- Use focused integration or unit tests for contracts, pure logic, boundary cases or failure modes they prove more directly and reliably. Explain their contribution when they supply primary evidence for a criterion. They complement complete journeys; isolated green checks do not establish that the assembled feature works.
- Keep the application behavior being verified real. Mock only external dependencies or unsafe side effects at their actual boundary, preserving realistic success and failure responses. Honor existing requirements to mock payment creation, refunds and other real-data effects. Identify every mocked boundary and the limit it places on the result; a mocked payment, report or provider response does not prove the external operation or deployed integration works. Never copy product logic into a fixture or substitute a fake component, handler or service for the behavior being claimed.
- Prevent flaky tests: isolate test data/state and await the action and its relevant follow-on work before asserting the completed outcome or starting the next action. This includes requests, rendering, animations and debounced or timer callbacks where applicable. Wait for every state the assertion relies on; the first visible row or callback does not prove all work has finished.
- For time-dependent behavior, use a controlled clock supported by the harness, advance the required time and await the observable result. With real time, use bounded waits for a specific readiness or completion condition. Never rely on machine speed, arbitrary sleeps or guessed delays. Extra retries, longer timeouts, swallowed errors, weakened assertions and skipped required cases must not conceal a race or defect.
- Finish or cancel owned asynchronous work before releasing the test environment, including work started by reset, intermediate unmount and final cleanup. Keep required browser globals alive until cleanup completes. When cancellation or unmount during pending work is the behavior under test, deliberately trigger it while work is pending, then verify cancellation and the absence of late effects; do not settle the work first and bypass the scenario.
- For a bug, prove a representative submitted regression fails on the exact buggy baseline for the reported behavior before expanding it. A harness/import failure is not a behavioral failure. For new behavior, use the approved early-evidence plan and meaningful negative controls where applicable. Preserve author independence: CoS and verification own candidate execution and counterexamples that would expose peer edits. Never add product stubs just to execute a test.
- In the existing handoff, map acceptance criteria to the executed evidence and list untested criteria, mocked boundaries and unavailable runtime proof. Report what the green result demonstrates in the tested environment. Do not declare the feature verified while required journey evidence is missing, blocked, skipped or replaced by a weaker substitute; a green subset or test count cannot stand in for that proof. No suite guarantees the absence of every bug.

Isolate the trigger being tested: keep unrelated refresh inputs fixed, wait for an observable completion rather than a default value, and mount the actual consumer for lifecycle claims. At the permitted integration or repair stage, prove the actual submitted regression fails on the exact buggy source or a minimal wrong-behavior overlay. Preserve initial author independence. A reviewer probe or harness error is not submitted-test proof. Report the failing assertion and both source identities.
